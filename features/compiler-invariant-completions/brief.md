# Compiler Invariant Completions — Product Brief

**Created:** 2026-05-07
**Last updated:** 2026-05-12

## Problem

The compiler ships with several stated invariants whose enforcement still depends on contributor diligence rather than CI, and several residual defects from prior work whose closure was deferred under the project's "no deferred correctness" rule. Each gap is contained — a single rule, a single regenerator, a single missing constructor, a single transitional payload, a single placeholder field name — but each represents the failure class the project's discipline was written to exclude:

- **Duplicate diagnostics on the same defect.** When an author commits a name collision across the hero, replica-item, and monster categories, the compiler emits two findings for the same mistake — one from the narrower cross-bucket rule, one from the broader cross-category rule. The author cannot tell whether they have made one error or two; an LLM author with limited context wastes effort triaging duplicates against a defect that is singular in the source code.

- **IR shape variants without corpus evidence.** The IR carries shape variants that no reference mod actually produces. Carrying a shape with zero corpus instances is a hypothesis: rules and tests written against it describe behavior that never executes against real mod input, and the next contributor who builds on the unevidenced variant compounds the defect. The audit's first run is the authoritative inventory of which shipping variants are currently unevidenced.

- **Generated source not asserted byte-deterministic.** The build process runs the corpus through harvesters that emit generated source files. Those files must be byte-identical across runs so a build on machine A produces the same generated source as on machine B — important for reproducible builds, the future browser-app pipeline, and CI determinism. The harvester is structured to be deterministic, but no test verifies this; a future regression (introducing wall-clock input, environment-variable input, or hash-map iteration order) fails silently until someone notices the generated source diverges across machines.

- **IR variant payload that bypasses the IR shape with raw bytes.** The `ItempoolItem::NonSummon` IR variant currently carries a `content: String` field that holds every byte of a non-summon itempool entry's body verbatim — a transitional raw-passthrough that defeats SPEC §3.2 (no `raw: String` escape hatch in typed IR). Any field-contents-bypass in a corpus-evidenced variant is the same failure class as a discriminator-bypass: a hypothesis-as-model where structured IR is replaced by raw bytes, defeating SPEC §3.2 / §3.7 / §3.3 at one site.

- **Derived-structural regenerator with a deferred-correctness sink, plus one regenerator with malformed output.** The compiler's `merge` strips derived structurals and `build` regenerates them from content. Today three regenerators ship (`generate_char_selection`, `generate_hero_pool_base`, `generate_hero_item_pool`); one kind (`PoolReplacement`) remains an explicit `// PoolReplacement regenerator deferred.` wildcard arm in `regenerate_derived_kinds`. Separately, `generate_char_selection` emits a malformed body (`1.ph.s@1<mn_name>@1<mn_name>…`) where each `@1<name>` is a free-standing SeqPhase button with no `@2` action — not the canonical form documented in `reference/textmod_guide.md` §SeqPhase, which shows `ph.sChoose a Party@1[<Hero1>][<Hero2>]…@2!mparty.<Hero1>+<Hero2>+…` (one button containing the full party list of bracketed hero labels, followed by an `@2!mparty.` add action). The four reference mods (`working-mods/{sliceymon,pansaer,punpuns,community}.txt`) do not themselves export a derived char-selection Selector for round-trip — they rely on the base game's char-selection UI — so the Selector regenerator's correctness against the canonical form is verified by source-vs-IR divergence on synthesized heroes rather than by four-mod byte-match (which carries the load on `HeroPoolBase` / `ItemPool` / `PoolReplacement`, where the corpus does evidence derived instances). Both regenerator defects are unshipped derived-structural completions inherited from prior work.

- **Authorable IR types missing their construction primitives.** `HeroBlock`, `ReplicaItem`, `AbilityData`, and `TriggerHpDef` all ship without `::new(identity)` constructors. Sprite-bearing constructors were deferred when the sprite-consolidation work landed and have not shipped since. Authors today hand-spell every field.

- **Itempool extractor stub and message-coupled xref test predicates.** The current `extract_from_itempool` stub demotes every itempool entry to `ItempoolItem::NonSummon { content: <whole pool> }`, producing zero `Summon(usize)` entries from extracted corpus input. The sliceymon corpus contains roughly two dozen summon envelopes that the stub does not classify; sliceymon's `roundtrip_baseline` test (`compiler/tests/roundtrip_baseline.rs`) today reports `replica_items.count: 0 -> 0` and is expected to land at `23 -> 23` once the real classifier produces typed `ItempoolItem::Summon` entries (the per-trigger split is engineering-plan territory bound at chunk-authoring time). Cross-IR `Finding` values today carry cross-bucket information only as comma-joined prose in the user-facing message field; production xref rules dispatch on typed owner-map tuples internally, but every external consumer (test assertions, downstream tooling) must substring-scan the user-facing message to recover the bucket set, coupling diagnostic wording to the test surface. The Red Orb summon entry in sliceymon also carries a nested `hat.egg.(wolf.n.Geyser…` inside its outer `hat.egg.dragon.n.Groudon` envelope; today's `enemy_template: String` field on `ReplicaItem` captures only the outer template envelope, so a real classifier must extend the schema to represent the nested enemy bytes (shape bound in `decisions.md`).

- **Authority-doc vocabulary describes retired IR shapes.** `SPEC.md` carries one §10 glossary entry naming "Capturable / Legendary" as roles a `ReplicaItem` can fill; the entry itself disclaims the terms as IR identifiers and frames them as player-facing game-design vocabulary, but its presence makes the §10 glossary a vocabulary surface a downstream LLM author reads alongside the IR taxonomy. In-source code-comment surfaces (an X003 doc-comment parenthetical, an X003 owner-map bucket-label literal) likewise still speak retired IR identifiers, with the owner-map literal's rename bound in `decisions.md` and scoped to the dedupe chunk. The actual IR (post-Chunk-9) has neither variant — `ReplicaItem` is a single flat shape with `SummonTrigger`-axis variation; the surviving authority-doc and code-comment surfaces lag behind the shipped shape.

- **`ReplicaItem` carries a placeholder field name.** Today the summon-target field ships as `target_name`, a transitional placeholder carrying Pokemon-specific authoring vocabulary. This work retires the placeholder in favor of the generic `summon_name`.

These are residuals — every other foundational platform property has shipped and is enforced. Until they are closed, the compiler's stated invariants are partially aspirational, contributors cannot rely on the test suite to catch their own drift, and the typed authoring surface carries deferred-correctness debt that compounds with every chunk that builds on it.

## Solution

Close each invariant with an automated check that fails the test suite when the invariant is violated; close each residual defect with an atomic same-chunk landing per SPEC §3.7 / CLAUDE.md "no deferred correctness"; and remove any IR shape variant whose claim contradicts the new corpus-evidence rule. After this work lands, every invariant the compiler asserts is enforced — contributors discover violations at test time, not via a downstream review round — and every deferred residual from prior work closes. The invariants are existing project discipline; this work makes them executable. Every restructuring required to deliver these properties preserves the library-first / no-`std::fs`-in-library / round-trip-fidelity invariants SPEC §3.4 / §3.1 commit to — no carve-out admitted.

## Goals

- **Each cross-IR defect surfaces under exactly one rule.** A duplicated name produces exactly one finding regardless of how many categories share it. The two rules' domains partition the collision space without overlap (narrowing predicate bound in `decisions.md`). *Verified by:* an IR with a name collision across the hero, replica-item, and monster categories produces exactly one finding from the narrower rule (today produces two, one per rule); a two-category collision within {hero, replica-item, monster} likewise produces exactly one finding from the narrower rule; a four-category collision that includes boss produces exactly one finding from the broader rule, with the narrower rule staying silent because the category set includes boss; an intra-bucket duplicate produces exactly one finding from the broader rule, confirming the broader rule still owns the cases the narrower rule cannot cover.

- **Every IR shape variant is corpus-evidenced or explicitly an escape-hatch.** A new automated check walks the two classes of input-bytes-determined IR shape bound in `decisions.md` (enum variants in IR enums whose variant choice depends on the input mod; the unknown-sprite escape hatch used when the input mod references a sprite name not in the build-time registry) and asserts each resolves to an instance in the reference corpus or is present in a closed escape-hatch registry the audit reads mechanically. The registry is closed at exactly two entries — the unknown-face-ID enum variant and the unknown-sprite escape hatch — and future candidate escape-hatches require a brief amendment that adds them explicitly (see `decisions.md`); the audit does not honor a per-variant marker scheme. The walk follows the transitive closure of input-bytes-determined enums reachable from `ModIR` (bound in `decisions.md`), so future IR-reachable enums are audit-covered without per-enum opt-in. Adding an entry is a registry diff visible to review, not a hidden audit edit. Enums whose presence in the IR is determined by the compiler's internal state machine rather than the input mod's bytes are out of scope (provenance tags, classifier tags, and source filters today). Shapes that pass neither test are removed in the same change that lands the audit, along with any rules and tests authored against them. *Verified by:* the audit fails closed when an in-scope shipping IR shape is neither corpus-evidenced nor present in the registry; the first run identifies which (if any) shipping shapes are currently unevidenced, each of which is removed via a per-shape decisions-log entry before the audit lands green.

- **Generated build artifacts are byte-deterministic, asserted by CI.** Two runs of the build harvester against the same corpus produce identical output for every file the harvester emits. Scope: the build-time code-generation step that produces compiled-in source from the reference corpus — not `build(ir) → textmod` whole-mod emission, whose byte-determinism is not currently a SPEC-committed invariant and is out of scope for this work. The future browser/mobile mod-builder app (SPEC §1 vision pillar 4) requires deterministic generated source so the WASM artifact built from that source is reproducible across machines; this Goal locks the property at the harvester layer. *Verified by:* the test exercises the build-time harvester logic in a way that surfaces any process-distinguishable input as a byte divergence in any generated file; absent any such regression, both invocations produce byte-identical output for every generated file; the resulting harvester core is reachable from library code without importing `std::fs` or `std::process` (SPEC §3.4). The mechanism is engineering-plan territory; the brief commits to the property, not the mechanism.

- **No IR variant payload bypasses the IR shape with raw bytes.** The compiler's IR carries no variant whose payload is a raw `String` / `Vec<u8>` / `serde_json::Value` blob holding bytes that the parser refused to type. Today exactly one IR variant violates this: `ItempoolItem::NonSummon`'s `content: String` field carries every byte of a non-summon itempool entry's body verbatim — a known SPEC §3.2 violation tracked at the IR doc-comment level. The fix retypes `NonSummon`'s payload to a fully typed schema whose variants cover every observed non-summon itempool entry shape across the four reference mods (per-variant shape bound in the typed-NonSummon-payload chunk plan), in one atomic commit migrating every callsite (no parallel representation, no deferred replacement; SPEC §3.2 / §3.7 / CLAUDE.md "no deferred correctness"). *Verified by:* the four-mod round-trip equality bar holds post-rewrite against the typed schema; per-variant round-trip guards prove each typed variant's emitter is byte-equal against its source bytes; the variant-evidence audit Goal above extends automatically to walk the typed-payload variants as in-scope IR enum variants; a permissive-extract pressure-valve variant is retained per SPEC §3.3 so novel itempool entry shapes demote to a paired `Finding` + typed variant rather than a raw escape, with its budget ratcheted against the current four-mod count so future shape evolution lands a paired typed variant rather than growing the pressure valve.

- **Derived-structural regenerators are complete and corpus-matched.** Every structural-modifier kind that the build derives from content has a regenerator that produces byte-output matching the format spec. The remaining deferred regenerator (`PoolReplacement`, today a `// PoolReplacement regenerator deferred.` wildcard arm in `compiler/src/ir/merge.rs::regenerate_derived_kinds`) lands; the existing `generate_char_selection` regenerator's malformed body shape is corrected to match the canonical SeqPhase form documented in `reference/textmod_guide.md` (one button containing all bracketed hero labels + an `@2!mparty.` add action, not the current `1.ph.s@1<mn_name>…` free-standing-buttons shape). *Verified by:* `HeroPoolBase` and hero-bound `ItemPool` regenerators produce output that byte-matches the source-extracted instance across all four reference mods; the `PoolReplacement` four-mod byte-match against `working-mods/punpuns.txt`'s `((heropool.<list>)&Hidden).doc.<text>.mn.<name>` body — including the inline `(replica.<X>.abilitydata.(...)).n.<X>` rows interleaved with bare hero names — is delivered by the typed-payload sibling chunk per decisions.md 2026-05-19, which widens `StructuralContent::PoolReplacement` from a raw-`body: String` shape to typed fields covering `&Hidden`, `.doc`, `.mn`, and a typed `Vec<PoolReplacementEntry>` sum modeling both bare-hero rows and inline-replica rows, widens the parser, emitter, and `generate_pool_replacement` accordingly, and flips the extractor's `derived` initialization for `PoolReplacement` so the strip-and-regen cycle actually runs on extracted content; the `complete-regenerators` chunk delivers the canonical-shape `generate_pool_replacement` for the `derived: true` synthesized case (the structurally minimal `((heropool.<list>))` form before the typed-payload sibling chunk widens it), the `DerivedKind` exhaustiveness machinery, the outer/inner dispatch split, and the `generate_char_selection` body rewrite; the `Selector` regenerator's correctness is verified by source-vs-IR divergence on synthesized heroes against the canonical form per `reference/textmod_guide.md` §SeqPhase, since the four reference mods rely on the base game's char-selection UI and do not export a derived char-selection Selector for round-trip; per-regenerator source-vs-IR divergence tests prove each regenerator reads from content (the hero list, the replica-item list, the structural-modifier set), not from a registry or canonical source.

- **Every authorable IR type has a construction primitive that requires identity at construction.** Each of the four authorable types (`HeroBlock`, `ReplicaItem`, `AbilityData`, `TriggerHpDef`) ships a `::new(...)` constructor whose required arguments are the type's identity-bearing fields (specific signatures determined by the engineering plan against the current IR shape); the required-identity fields are non-defaulted by construction, and no `Default` derive ships for any of the four — an emitter cannot receive an instance whose required identity bytes are empty. *Verified by:* unit tests construct an instance of each of the four types via its `::new` constructor and assert the required identity fields are populated; a guard test asserts none of the four types implements `Default`.

- **The itempool extractor produces typed summons; cross-IR findings carry typed cross-bucket fields.** The stub `extract_from_itempool` is replaced with a real classifier that detects corpus-evidenced summon shapes — a conjunctive `hat.egg.<enemy>` + `vase.(add.((replica.<team>.n.<same-Pokemon>…)))` pair plus a trigger-wrapper match — routing matches to `ItempoolItem::Summon(i)` + a populated `ReplicaItem` and delegating non-matches to the typed `NonSummonEntry` path. The `ReplicaItem` schema widens in the same commit to model nested enemy templates (today's `enemy_template: String` cannot capture the Red Orb shape `hat.egg.(wolf.n.Geyser…)` nested inside `hat.egg.dragon.n.Groudon`); the schema-widening shape is bound in `decisions.md` to a recursive sum, and the property — no nested-egg bytes silently lost AND every depth-N nesting in the source bytes is structurally encoded in the IR (flat sequences are excluded) — is in scope here. Cross-IR `Finding` widens with typed cross-bucket fields whose representation is engineering-plan territory; the two collision-detection rules dispatch on those typed fields rather than on message-prose substring scans. *Verified by:* the four-mod round-trip equality bar holds with the typed classifier producing real summons (sliceymon `replica_items.count: 23 → 23`; pansaer / punpuns / community stay `0 → 0`); a source-vs-IR adversarial test pair proves classification reads inner payload bytes rather than container-name substrings; the two collision-detection rules' test assertions match on typed `Finding` fields rather than message-substring containment; no `message.contains` predicate over bucket-label literals survives in the test suite.

- **SPEC.md and authority-doc vocabulary match the shipped IR.** `SPEC.md` carries no live-normative entries for retired ReplicaItem kinds; the prose describes the `SummonTrigger`-axis taxonomy that actually ships. *Verified by:* targeted greps against `SPEC.md` for the retired-type parentheticals and classifier-ASCII tokens return zero hits; the §10 glossary entry's heading carries no retired IR-identifier names while its player-facing role description survives (disposition bound in `decisions.md`); the §6.3 uniqueness invariant ("at most one of: heroes, replica items, monsters") and its CRUD-enforcement sentence survive verbatim; a permanent guard test in `compiler/tests/` enforces the SPEC vocabulary going forward.

- **`ReplicaItem` summon-name vocabulary is generic, not Pokemon-specific.** The `target_name: String` field on `ReplicaItem` is renamed to `summon_name: String`. The rename is atomic across every callsite per SPEC §3.7 / CLAUDE.md "no deferred correctness"; a permanent retirement-protocol guard test enforces the new name going forward. *Verified by:* `rg "target_name"` against `compiler/src/**/*.rs` returns zero hits modulo the documented retirement-comment exception; the existing test suite passes against the renamed field with no parallel `target_name` field surviving.

## Non-goals

- **No re-prosecution of already-shipped platform invariants, with bounded carve-outs for explicit deferred residuals.** Structured errors with field-path and suggestion, typed face and sprite identifiers, source-filtered build emission, finding provenance, in-place merge with strip-and-regen for corpus-evidenced derived structurals, and the panic-free library audit are all shipped today and are not touched. **Bounded carve-outs**: (a) the `PoolReplacement` regenerator + `generate_char_selection` body-shape correction under the complete-regenerators Goal close two regenerator-side residuals (the deferred `PoolReplacement` regenerator and the malformed `generate_char_selection` body) inherited from prior work — they author missing or malformed regenerators paralleling the three shipped ones, not re-opening the strip-and-regen contract; (b) the four `::new` constructors (`HeroBlock`, `ReplicaItem`, `AbilityData`, `TriggerHpDef`) under the construction-primitives Goal close constructor residuals inherited from prior work — sprite-bearing and identity-bearing constructors deferred at the sprite-consolidation landing have not shipped since.

- **No new author-ergonomics surface, with bounded carve-outs.** The compiler's existing typed authoring layer (typed face and sprite primitives plus the type-state replica-item builders that already ship) is treated as terminal for platform purposes. Further chainable builders, dice macros, or hero-replica composition belong to a future author-ergonomics feature. **Bounded carve-outs**: (a) the typed `NonSummonEntry` authoring builders required by the typed-NonSummon-payload Goal (`compiler/src/authoring/non_summon_entry.rs`) — the SPEC §3.3 strict-validation site paired with the SPEC §3.2 typed-IR commitment; (b) the four `::new` constructors (`HeroBlock`, `ReplicaItem`, `AbilityData`, `TriggerHpDef`) required by the construction-primitives Goal. Both carve-outs are bounded by enumeration: (a) covers one module and one typed sum; (b) covers four `::new` constructors. No other authoring expansion is admitted by this feature.

- **No parser or emitter behavior changes beyond what the five bounded carve-outs require.** Round-trip fidelity across the four reference mods stays the correctness bar; any extractor or emitter change is bounded to: (a) the strip-and-regen path that retires alongside a deleted variant under the variant-evidence audit Goal; (b) the typed `NonSummonEntry` classifier + emitter under the typed-NonSummon-payload Goal; (c) the real summon prefilter + `ReplicaItem` nested-egg schema widening under the typed-summon-extractor Goal — widening bounded to the recursive-sum `enemy_template` field shape bound in `decisions.md` 2026-05-12; no other `ReplicaItem` field reshapes admitted under this carve-out; (d) the `generate_pool_replacement` + `generate_char_selection` body-shape corrections under the complete-regenerators Goal; (e) the `StructuralContent::PoolReplacement` typed-payload widening — `parse_poolreplacement` widens to populate the typed `&Hidden` / `.doc` / `.mn` fields and the `Vec<PoolReplacementEntry>` sum, the emitter arm reconstructs from those typed fields, and the extractor's `make_structural` flips `derived: false → true` for `PoolReplacement` so the strip-and-regen cycle runs on extracted content — under the typed-payload sibling chunk per decisions.md 2026-05-19. Specifically excluded: any reshape of the hero / monster / boss extractors, any reordering of canonical emission output, any change to dice-face emission, and any modifier-parser change outside the five carve-outs.

- **No drift-class parser/emitter fixes outside the five bounded carve-outs above.** The OPEN PIPELINE_FIDELITY drift classes catalogued today, plus the `HiddenModifierType::Skip` placeholder waiting on reward parsing in `compiler/src/extractor/structural_parser.rs`, are owned by a future pipeline-fidelity feature scoped to land at `features/pipeline-fidelity/`. This feature does not touch them, and the round-trip equality bar on the four reference mods — which already holds today despite those open classes — is the correctness bar this work meets.

- **No game-balance, roster, or corpus changes.** This is platform work — the reference-mod corpus and any downstream mod's content are unaffected. Corpus-evidence audits work against the four reference mods as they stand; if the audit's first run identifies any shipping IR shape as unevidenced, the deletion (and its doc-surface bundle per `decisions.md`) lands within the audit's own chunk.

- **No expansion of *author-content* cross-IR semantic checks beyond deduplicating the two existing collision rules.** New author-content cross-IR rule categories — additional collision dimensions, new uniqueness scopes, exhaustiveness checks over author-supplied identifiers — belong to a future feature. The dedupe Goal reassigns shared cases to the narrower rule and trims the broader rule to its non-overlapping residual; it does not authorize adding new author-content rules while in the area. The variant-evidence audit Goal is a structural check on IR-shape against the corpus, not an author-content rule, and is in scope here.

## User-facing changes

- A name shared across the hero, replica-item, and monster categories produces one diagnostic per defect, not two.

- The test suite includes a new audit that fails if any in-scope IR shape is neither corpus-evidenced nor on the closed escape-hatch registry. Adding an in-scope hypothesis-only shape in a future change fails CI.

- The test suite includes a new audit asserting the compiler's generated source files are byte-identical across repeated harvester invocations against the same corpus, with the test surfacing any process-distinguishable input as a byte divergence in any generated file. A regression that introduces non-determinism fails CI.

- If the audit's first run identifies any in-scope shipping IR shape as unevidenced, that shape (and any rules and tests authored against it, including any dormant arm of the merge strip-and-regen path that targeted it) is removed, and every authority document that names the specific derived-structural kind being deleted is amended to drop any corresponding entries.

- The compiler's IR retypes the `ItempoolItem::NonSummon` variant's payload from a raw `content: String` blob to a fully typed `NonSummonEntry` sum covering every observed non-summon itempool entry shape across the four reference mods; the four-mod round-trip equality bar holds against the typed schema; per-variant round-trip guards prove each typed variant emits byte-equal to its source bytes; the variant-evidence audit extends automatically to walk `NonSummonEntry`'s variants. Novel itempool entry shapes that don't match a typed variant produce a paired `Finding` rather than silently round-tripping as raw bytes (per SPEC §3.3).

- Building a mod whose source had `PoolReplacement` structurals reproduces them byte-for-byte after merge strip-and-regen. The `generate_char_selection` regenerator produces the corpus body shape (per-hero bracketed labels + party-add effect + variable assignment) rather than the prior malformed body. All four derived-structural kinds (`Selector`, `HeroPoolBase`, hero-bound `ItemPool`, `PoolReplacement`) regenerate symmetrically; the `_ => {}` deferred sink in `regenerate_derived_kinds` is retired.

- The compiler's IR retypes the `StructuralContent::PoolReplacement` variant's payload from a raw `body: String` blob to typed fields — `hidden: bool` (the `&Hidden` flag), `doc: Option<String>` (the `.doc.<text>` payload), the existing `name: Option<String>` on `StructuralModifier` (the `.mn.<name>` suffix, already extracted), and a `Vec<PoolReplacementEntry>` sum covering both bare-hero-name rows AND inline `(replica.<X>.abilitydata.(...)).n.<X>` rows observed in `working-mods/punpuns.txt`; the four-mod round-trip equality bar holds against the typed schema; per-entry round-trip guards prove each typed variant emits byte-equal to its source bytes; the variant-evidence audit extends automatically to walk `PoolReplacementEntry`'s variants. The extractor's `derived` initialization for `PoolReplacement` flips from `false` to `true` so the strip-and-regen cycle runs on extracted content; `generate_pool_replacement` widens to read from the typed fields and emits canonical bytes that byte-match the source-extracted instance.

- Authoring any of the four authorable IR types (`HeroBlock`, `ReplicaItem`, `AbilityData`, `TriggerHpDef`) no longer requires hand-spelling every field; `::new(identity)` constructors provide the minimal-required-fields path on each, and the required identity fields are non-defaulted by construction.

- Extracting a mod with `extract_from_itempool` produces real `ItempoolItem::Summon(usize)` entries plus populated `ReplicaItem` values when the source contains corpus-evidenced summon shapes; `extract(build(extract(mod))) == extract(mod)` holds against the real classifier across the four reference mods. The `ReplicaItem` schema widens to model nested enemy templates so the Red Orb shape (`hat.egg.(wolf.n.Geyser…)` inside `hat.egg.dragon.n.Groudon`) round-trips byte-equal rather than silently losing the nested bytes. Cross-IR `Finding` values carry typed `buckets: Vec<&'static str>` and `includes_boss: bool` fields rather than embedding cross-bucket information in user-facing message prose; xref predicates dispatch on the typed fields.

- `SPEC.md` no longer describes retired Capture / Legendary `ReplicaItem` kinds as live IR identifiers; its prose describes the `SummonTrigger`-axis taxonomy that ships, with the §10 glossary entry retaining its player-facing role description but stripping the retired IR-identifier names from the heading (disposition bound in `decisions.md`).

- The `ReplicaItem.target_name` field is renamed to `summon_name` in one atomic migration per SPEC §3.7; CLI / library consumers of `ReplicaItem` reference the field by its new name. No parallel `target_name` field survives.

## Open questions

None — every product-level question is resolved; cross-chunk wiring and bound disposition decisions live in `decisions.md`, and the two engineering-plan-layer mechanism choices below are delegations to the engineering-plan layer, not unresolved product questions.

## Engineering-plan hand-offs

Product-level scope and chunk-DAG cross-chunk wiring are bound in `decisions.md`. Two engineering-plan-layer mechanism choices are explicitly delegated to the engineering plan — the brief commits to the property at each Goal:

- The harvester-determinism Goal's verification mechanism. The property is bound at the Goal; the structural enabler — pure-core invokable outside `cargo build`, `&[(name, contents)]` input shape, shell strictly in `build.rs` — is bound in `decisions.md`; the specific verification mechanism is engineering-plan territory.
- The typed-NonSummon-payload Goal's `NonSummonEntry` variant set. Empirical from the chunk's corpus walk; per-variant arbitrations live in the typed-NonSummon-payload chunk-plan's decisions sidecar (location bound in `decisions.md` 2026-05-11 amendment), which is binding for chunk-internal variant decisions while cross-chunk wiring stays in this feature's `decisions.md`.
