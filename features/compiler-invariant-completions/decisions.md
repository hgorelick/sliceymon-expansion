## 2026-05-15 — `InternalStateEnum` syn-walker match mechanism, outer-rustdoc-attestation filter, crate-root re-export binding

**Decision:** Three refinements to the bound `InternalStateEnum` opt-out vehicle marker, surfaced during round-1 review of the `audit-marker` chunk plan.

1. **Syn-walker match key is the trait path's last segment, not bare-identifier text.** `audit-harness`'s Layer-1 walker matches `syn::ItemImpl.trait_` whose path's final segment (`syn::Path::segments.last()`) equals `InternalStateEnum`. Both bare (`impl InternalStateEnum for X {}`) and path-qualified (`impl crate::audit_markers::InternalStateEnum for X {}`, `impl textmod_compiler::InternalStateEnum for X {}`) impl forms resolve under the same match key — both end in the same final segment. **This refines `decisions.md` 2026-05-13 "Audit chunk implementation form"**, which described the walker as matching `impl InternalStateEnum for X` text; the text-match form was under-specified for the path-qualified case, which is valid Rust at every consumer site. The path-segment mechanism is the syntactic mechanism that the bound Walk-Layer-1 ("`syn` source-parse over `compiler/src/**/*.rs`") implements.

2. **Outer-rustdoc-attestation filter (`AttrStyle::Outer`) is mandatory.** The marker-misuse-mitigation row in `decisions.md` 2026-05-14 "Vehicle marker semantics" bound the `syn`-walker to enforce *presence* of at least one `Attribute` whose path resolves to `doc` on every `impl InternalStateEnum for X {}`. This entry adds the placement constraint: the audit's `syn`-walker filters `ItemImpl.attrs` to entries where `Attribute.style == AttrStyle::Outer AND` the attribute path resolves to `doc`. The mandatory placement is an outer `///` doc-comment immediately above the `impl` line; inner `//!` doc-comments inside the impl block (which attach with `AttrStyle::Inner`) and `///` doc-comments placed between the impl block's `{` and `}` (which attach to the next nested item, of which an empty impl block has none) do NOT satisfy the attestation. **This refines `decisions.md` 2026-05-14 "Vehicle marker semantics"** by pinning the AST placement filter; the 2026-05-14 entry's broader mechanism binding remains in force.

3. **Crate-root re-export `pub use audit_markers::InternalStateEnum;` is required.** The `audit-marker` chunk adds the re-export to `compiler/src/lib.rs` immediately after the existing `pub use ir::Source;` line, matching the established crate-root re-export pattern for sibling pub IR-adjacent types (`pub use ir::Source;`, `pub use finding::{Finding, Severity};`). Downstream consumer chunks (`audit-marker-retrofit`, every Foundation-wave chunk landing a new ModIR-reachable internal-state pub enum) import the trait via the canonical path `textmod_compiler::InternalStateEnum` (out-of-crate) or `crate::InternalStateEnum` (in-crate). The longer-form paths `textmod_compiler::audit_markers::InternalStateEnum` and `crate::audit_markers::InternalStateEnum` remain valid Rust under the path-segment match mechanism (point 1 above), but the bare crate-root form is the canonical consumer-import path. The re-export is load-bearing for consumer-import-path stability: a future refactor moving the trait to a different sub-module path (e.g. `compiler/src/audit/markers.rs`) breaks every consumer using the longer-form path; consumers using `textmod_compiler::InternalStateEnum` remain stable across such moves. This is a new binding — no prior `decisions.md` entry addressed the crate-root re-export question.

**Why:** Each refinement closes a class of cross-chunk contract ambiguity that surfaced during chunk-plan review. (1) Without the path-segment mechanism, the `audit-harness` chunk plan would have to choose between two non-equivalent regex forms (bare vs path-qualifier-tolerant) — and the bound `audit-marker` chunk plan was internally inconsistent (claimed bare-identifier match key in its §Conventions while using path-qualifier-tolerant pre-implementation grep regexes in §Tests-to-add and §Acceptance-criteria). The syntactic `Path::segments.last()` mechanism resolves both forms uniformly. (2) Without the `AttrStyle::Outer` filter, a contributor placing an inner `//!` doc-comment inside the impl block bypasses the mandatory rustdoc-on-impl attestation while passing a naive `attrs.iter().any(|a| a.path().is_ident("doc"))` check — exactly the silent-bypass class the marker-misuse-mitigation was designed to prevent. (3) Without the mandatory re-export, consumer chunks (foundational and forward-binding) choose between two non-equivalent import paths; the longer-form path is fragile under future module refactors that the existing re-export pattern explicitly absorbs.

**Promotion source:** This entry captures three refinements raised during `/plan-review-v2` of `audit-marker.md` (round 1) by the architecture persona. The three refinements are not contradictions of the 2026-05-13 and 2026-05-14 bound entries — they are mechanism-pinning extensions that those bound entries delegated to the chunk-plan layer; the round-1 review surfaced that pinning them at the `decisions.md` layer (rather than chunk-plan layer) is required because they are forward-binding obligations on every downstream Foundation-wave chunk introducing a new ModIR-reachable internal-state pub enum.

**Rejected:**
- Keep "bare-identifier text match" for the syn-walker — under-specified for path-qualified impl forms, internally inconsistent with the path-qualifier-tolerant pre-implementation grep regexes in the chunk plan's tests-to-add bullets.
- Keep `Attribute path resolves to doc` filter without `AttrStyle::Outer` — admits inner-doc-comment misuse as silent attestation bypass.
- Leave crate-root re-export as "implementer's call" — defers a Class B cross-chunk wiring decision (consumer-import-path stability) to chunk-internal Class C, contradicting the established crate-root re-export pattern for sibling IR-adjacent pub types and creating a future-refactor brittleness class.
- Add the path-segment mechanism + outer-attr filter inside the `audit-harness` chunk plan only — defers the binding to a downstream chunk plan that doesn't yet exist; foundational-chunk authoring would proceed with under-specified contract, and every Foundation-wave chunk attaching the marker would face the same ambiguity individually.

## 2026-05-14 — Harvester SHA ledger consolidation: one-time check stays in `harvester-pure-core`

**Decision:** The one-time pre-vs-post SHA-256 divergence check for `face_id_generated.rs` + `sprite_registry_generated.rs` happens entirely within `harvester-pure-core`'s PR. That chunk captures the pre-refactor SHA at its opening, runs the pure-core extraction, captures the post-refactor SHA at its closing, compares them in its own acceptance criterion, and is REJECTED on divergence per `decisions.md` 2026-05-11 round-1 resolution. The ledger artifact is the chunk's PR-attached test evidence. `harvester-determinism-audit` does NOT carry the one-time refactor-time check; it ships only the recurring CI determinism gate (the `audit_harvester_determinism.rs` in-process double-invocation test against `include_str!`-baked corpus), which runs on every subsequent CI invocation and gates future regressions introducing process-distinguishable input.

**Why:** The natural-reading mapping of decisions.md 2026-05-11 round-1 resolution ("the chunk is REJECTED on divergence") is that "the chunk" is the chunk doing the extraction — in the decomposed two-chunk shape, that's `harvester-pure-core`. Splitting the SHA dance across two PRs ("captured in chunk 1, consumed in chunk 2") would leave `harvester-determinism-audit` carrying a rejection semantic for a `harvester-pure-core` defect, which inverts the rejection ownership. The one-time refactor-time check and the recurring CI gate are genuinely separate concerns: the SHA divergence check assures the refactor itself is byte-equivalent (a one-shot historical anchor); the recurring CI test gates *future* determinism regressions (an ongoing assertion). Consolidating each to its natural owner preserves both semantics.

**Rejected:**
- Pre-refactor SHA captured in `harvester-pure-core`, post-refactor SHA captured in `harvester-determinism-audit` — inverts the rejection ownership (the audit chunk would reject for a pre-existing pure-core defect it didn't introduce).
- Both SHAs captured inside `harvester-determinism-audit`'s integration test as a runtime check — confuses one-time refactor verification with recurring determinism gating; the recurring test cannot meaningfully compare against a "pre-refactor" state once `harvester-pure-core` has merged.
- Embed the pre-refactor SHA as a `const` in `harvester-determinism-audit`'s test code — adds a maintenance object that future contributors must update on every legitimate generated-source change, defeating the one-shot historical-anchor purpose.

## 2026-05-14 — Vehicle marker semantics (opt-out, not opt-in)

**Decision:** The `InternalStateEnum` marker trait declared in `compiler/src/audit_markers.rs` is an **opt-OUT** marker: applying `impl InternalStateEnum for X {}` attests "NOT input-bytes-determined; exempt from corpus-evidence walk." The audit's default for every Layer-1 pub enum in the audit scope that is also Layer-2-reachable from `ModIR` is "must be corpus-evidenced, registry-listed, or brief-deferred." Per-enum opt-OUT is applied at the declaration site for compiler-internal-state enums (e.g. `Source`, `StructuralType`, `Severity` — enums whose variant choice is determined by compiler internal state rather than input mod bytes per the corpus-evidence Goal's carve-out "provenance tags, classifier tags, and source filters today"). The closed escape-hatch registry remains at exactly two entries (`FaceIdValue::Unknown` + unknown-sprite name-membership) per `decisions.md` 2026-05-08; the registry is the brief-amendment-only carve-out for input-bytes-determined shapes that legitimately lack corpus evidence. Inverting semantics this way preserves the audit's role as a brief-anchored invariant: a new input-bytes-determined pub enum landing without explicit classification fails closed (default audit walk), not silently miss-passes. **Marker-misuse mitigation:** the opt-OUT semantic admits a silent-bypass risk (a contributor misapplying the marker to an input-bytes-determined enum bypasses corpus-evidence). The mitigation is mandatory rustdoc-on-impl discipline mechanically enforced by the audit's `syn`-walker (`ItemImpl.attrs` must contain at least one `Attribute` whose path resolves to `doc`); the audit cannot mechanically verify the doc-comment's content (a human-review obligation), only its presence. **Promotion source:** this entry promotes the engineering-plan `## Decisions closure` row "Vehicle marker semantics (opt-out, not opt-in)" to the durable decisions log. The engineering-plan row remains as a summary cite.

**Why:** Round-4 reviewer state `IMPLEMENTABILITY_GAP` "Input-bytes-determined vs internal-state enum classification mechanism" surfaced the opt-IN-vs-opt-OUT choice. Three alternatives considered. (A) **Opt-IN** (every audit-exempt enum carries an attribute like `#[audit_exempt]` or membership in a code-side list): rejected because every chunk introducing an input-bytes-determined enum would silently land without audit coverage if the chunk-author forgets to add it to the audit list — the audit's role as a brief-anchored invariant inverts; new pub enums default to "uncovered" rather than "must classify." (B) **Per-variant per-enum bidirectional attribute** (each enum carries an `#[audit_state(internal | input_bytes)]` attribute): rejected because it doubles the attribute surface and requires the audit to parse attribute payloads, expanding the `syn`-walker's correctness surface. (C) **Opt-OUT** (the marker attests "NOT input-bytes-determined"; default is "must be corpus-evidenced or registry-listed"): chosen because the default fails closed (a new pub enum landing without explicit classification triggers the audit), which preserves the brief-anchored invariant under the no-deferred-correctness rule. The silent-bypass cost is accepted with mandatory rustdoc-on-impl discipline; the cost of opt-IN (silent under-coverage of new enums) is structurally worse than the cost of opt-OUT (a contributor explicitly attaches a marker they should not have attached, with a rustdoc-discipline check catching the easy half of misuse). Per `_review-common/principles.md` cross-artifact authority order, this Class B (cross-chunk wiring) decision lives in `decisions.md` for durability across chunk-plan and engineering-plan retirements.

**Rejected:**
- Opt-IN per-enum attribute scheme (Option A above) — default fails open; new input-bytes-determined pub enums silently land without audit coverage if the chunk author omits the attribute. Brief-anchored invariant inverts.
- Per-variant bidirectional attribute (Option B above) — doubles the attribute surface; expands the `syn`-walker's attribute-parsing correctness surface; provides no advantage over opt-OUT.
- Marker-derivable from `JsonSchema` or similar reflection — `JsonSchema` derive is universal for IR types (every type derives it for SPEC §3.6); piggy-backing the marker on `JsonSchema` doesn't distinguish input-bytes-determined from internal-state enums.

The audit's existing CI-on-every-PR pattern (the bound `decisions.md` 2026-05-13 Cross-chunk vehicle classification row) provides the same gating mechanism for the extension obligation.

**Rejected:**

Pre-extending the list to name an identifier that has not yet entered the codebase is the brief-pre-naming failure mode `decisions.md` 2026-05-08 "Variant-deletion bundle is class-defined" rejected at the chunk-authoring layer.
- Bind the extension to `ir-shape-evidence-audit` regardless of merge order (the audit chunk always carries `DerivedKind` even if it merges first) — same defect as above; the audit chunk would name an identifier unbacked by its own working-tree state if it merges before `complete-regenerators`.
- Make `complete-regenerators` always carry the extension — same defect mirror-imaged: if `complete-regenerators` merges first, the audit's `REACHABILITY_CARVE_OUT` does not yet exist (declared inside `ir-shape-evidence-audit`'s chunk file). The "whichever merges second" rule resolves the asymmetry naturally.

## 2026-05-13 — Audit Layer-1 scope widened from four directories to `compiler/src/**/*.rs`

**Decision:** The variant-evidence audit's Layer-1 `syn` source-parse walk widens from `compiler/src/{ir,authoring,extractor,harvester}/**/*.rs` to `compiler/src/**/*.rs` (excluding `compiler/tests/` and `compiler/build.rs` — the audit covers library source, not test code or build scripts). **This entry supersedes the 2026-05-13 "Audit chunk implementation form" entry's clause** binding Layer-1 to four directories; the marker form (`pub trait InternalStateEnum {}`), the `schemars` Layer-2 introspection mechanism, and every other binding in that 2026-05-13 entry remain in force. The engineering-plan invariant `Cross-chunk vehicle classification` and the Decisions closure row `Existing pub enum partition retrofit scope` widen to the same scope. The chunk plan's §Partition extends with: `Severity` at `compiler/src/finding.rs` (Internal-state marker — Layer-2-reachable from `ModIR.warnings: Vec<Finding> → Finding.severity`, derives `JsonSchema`); `ErrorKind` at `compiler/src/error.rs` (Layer-2-unreachable carve-out — does not derive `JsonSchema`, held only on `CompilerError`); `SourceFilter` at `compiler/src/builder/options.rs` (Layer-2-unreachable carve-out — does not derive `JsonSchema`, held only on `BuildOptions`).

**Why:** The four-directory scope was authored before the first-run partition. Empirical verification against repo HEAD identified `Severity` (declared at `compiler/src/finding.rs` with `#[derive(... JsonSchema)]`) as Layer-2-reachable from `ModIR.warnings: Vec<Finding> → Finding.severity` but OUTSIDE the four-directory Layer-1 walk — the audit's Layer-1 ⊆ Layer-2 cross-check would fail at chunk-land. Three resolution paths were considered. (A) Widen Layer-1 scope to `compiler/src/**/*.rs`. (B) Relocate `Severity` and `Finding` into `compiler/src/ir/finding.rs`. (C) Allowlist `compiler/src/finding.rs` explicitly while preserving the four-directory rule. Path A is structurally correct AND generalizes against future crate-root pub enums without revisiting (e.g. a future declaration in `compiler/src/lib.rs` or `compiler/src/something_new.rs`); the decisions-log amendment is the standard append-only supersession pattern the feature uses elsewhere. Path A strictly dominates on correctness, follow-on cost, reviewer reaction (the engineering-plan invariant amends cleanly), and authority-order conformance (decisions-log entry follows the standard append-only pattern).

## 2026-05-13 — `DerivedKind` is single source-of-truth; `is_derived()` delegates

**Decision:** Inside the `complete-regenerators` chunk, `StructuralModifier::is_derived()` in `compiler/src/ir/mod.rs` is rewritten to delegate to `DerivedKind`: `self.derived && DerivedKind::try_from(&self.modifier_type).is_ok()`. The existing 4-variant `matches!` literal in `is_derived()`'s body retires. `DerivedKind`'s variant set becomes the **single source-of-truth** for which `StructuralType` variants are derived; `is_derived()` becomes a delegated predicate. Adding a fifth derived `StructuralType` requires only one step — extend `DerivedKind` with a corresponding variant — which then forces the inner exhaustive-match arm in `regenerate_derived_kinds`'s inner function at compile time AND auto-flips `is_derived()`'s output for the new variant (because `DerivedKind::try_from` now succeeds for it). The outer dispatch arm continues to silently no-op on `Err` since the `kinds` argument is built upstream by `collect_stripped_kinds`, which filters by `is_derived()` — and `is_derived()` returns true only when `DerivedKind::try_from` succeeds, making `Err` at the outer arm structurally unreachable.

**Why:** Round 5 chose to introduce `DerivedKind` to escape an exhaustiveness-over-`StructuralType` defect. Round 6 found that the round-5 chosen design had a NEW defect on a different vector: the outer arm's silent-no-op-on-`Err` reproduced today's `_ => {}` deferred-sink behavior on the exact regression class the chunk claimed to close (a future contributor flipping a fifth `StructuralType` variant to derived in `is_derived()`'s `matches!` without extending `DerivedKind` would cause `TryFrom` to return `Err`, the outer arm to no-op, and the inner exhaustiveness check to never reach the new variant). Three resolution paths were considered. (A) Drop `DerivedKind` entirely; replace the inner match wildcard with `_ => unreachable!()` after the upstream filter. Reverses round-5's decision; smaller code footprint but retracts a structural commitment. (B) Bind the outer arm to panic on `Err`. Keeps `DerivedKind` but the enforcement is runtime, not compile-time. (C) Rewrite `is_derived()` to delegate to `DerivedKind::try_from`. Keeps `DerivedKind`, eliminates the parallel encoding (the set is encoded once in `DerivedKind`'s variant list; `is_derived()` becomes a derived predicate), AND provides compile-time enforcement of the regression class — adding a derived variant requires extending `DerivedKind`, which forces the inner-match update. Path C dominates: smaller diff than (A), stronger enforcement than (B), and the CLAUDE.md "no parallel representations" rule is honored (one encoding of "which `StructuralType` is derived", in `DerivedKind`'s variant list). The brief Goal 5 verifier ("derived-structural regenerators are complete and corpus-matched") is honored unchanged; the chunk's atomic-landing binding (2026-05-12 "Complete-regenerators chunk lands `PoolReplacement` regenerator and `generate_char_selection` body-shape correction atomically") is preserved because Path C is an internal mechanism amendment, not a chunk split.

**Rejected:**
- Path A (drop `DerivedKind`) — reverses round-5's structural commitment, retracts compile-time enforcement of the derived-allowed-set, and the inner-match's `_ => unreachable!()` arm gives only runtime enforcement (the regression mode is detectable only when the corpus produces the unreachable case, not at compile time of the new variant).
- Path B (panic on `Err` in outer arm) — keeps `DerivedKind` without making it serve its purpose; the regression mode is detectable at first test run (panic message), not at compile time when the contributor adds the unbacked derived variant.
- Path D (split the chunk into regenerator-bodies + derived-dispatch-exhaustiveness siblings) — violates the 2026-05-12 atomic-landing binding; both regenerator edits land in the same dispatch function (`regenerate_derived_kinds`) and share the same four-mod regenerator dogfood, so splitting doubles overhead without independent dogfood.

## 2026-05-08 — Determinism audit requires harvester core invokable outside `cargo build`

**Why:** Goal 3 commits to a verifiable property the codebase's current shape cannot deliver without restructuring access to the harvester core.
