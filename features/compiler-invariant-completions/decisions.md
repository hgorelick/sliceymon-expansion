## 2026-05-13 — Audit chunk implementation form: marker trait + syn source-parse + schemars introspection

**Decision:** The `ir-shape-evidence-audit` chunk's three implementation surfaces are bound as follows. (1) **Marker form:** `pub trait InternalStateEnum {}` declared in a canonical IR module (chunk-plan picks the exact location — `compiler/src/ir/audit_markers.rs` or similar). Every chunk that introduces a new internal-state pub enum reachable from `ModIR` writes `impl InternalStateEnum for X {}` near the enum declaration (in the same module). (2) **Walk Layer 1 (pub enum declaration enumeration):** `syn` source-parse over `compiler/src/{ir,authoring,extractor,harvester}/**/*.rs` at test time. The walker discovers every `pub enum X` declaration AND every `impl InternalStateEnum for X` impl; the set difference is the universe to audit for corpus evidence. (3) **Walk Layer 2 (transitive reachability from `ModIR`):** `schemars::schema_for!(ModIR)` produces a `RootSchema` with a `definitions` map; the audit walks the schema graph (which traverses through `Box<T>` / `Vec<T>` / sum variants because every IR type derives `JsonSchema`) to identify which enums in the Layer-1 universe are reachable from `ModIR`. An enum reachable-and-unmarked-and-unevidenced fails the audit. The closed escape-hatch registry remains at two entries (`FaceIdValue::Unknown` + unknown-sprite escape hatch) per 2026-05-08; this entry binds the marker form, not the registry's contents. **This entry supersedes the 2026-05-11 "Deterministic variant-enumeration vehicle" entry on the walk-mechanism question** — that entry deferred the per-enum variant-enumeration mechanism to the chunk plan; this entry binds both layers of the walk at the engineering-plan layer because the cross-chunk surface (the marker symbol every chunk consumes) requires the form to be agreed in advance.

**Why:** Three forms were considered for the marker. (A) Stringly-typed const list at a canonical location was rejected because string-typed identifiers are fragile under rename (rename without updating the list → silent miss) AND every chunk introducing a new enum would amend a shared file, creating Foundation-wave merge conflicts. (B) Derive macro `#[derive(InternalStateEnum)]` was rejected because it requires adding a proc-macro crate to the workspace (new infrastructure) and the existing repo has no proc-macro crate to extend. (C) Trait impl + syn discovery wins because it (i) is class-defined — every chunk attaches independently in its own module, no merge conflicts; (ii) is rename-safe — `syn` parses the actual Rust syntax, so a rename of `X` to `Y` updates both the `pub enum Y` declaration AND the `impl InternalStateEnum for Y` impl atomically; (iii) requires no new runtime infrastructure. The class-defined marker form is the load-bearing property: it preserves Foundation-wave parallelism without `ir-shape-evidence-audit` having to land before chunks that introduce new internal-state enums (since any chunk can write the trait impl independently). For the reachability walk, `schemars` is already a runtime dep at `compiler/Cargo.toml` and every reachable IR type already derives `JsonSchema`; the chunk would otherwise have to invent a reflection layer.

**Rejected:**
- Stringly-typed const list — fragile under rename; shared-file merge conflicts; Foundation-wave parallelism broken.
- Derive macro — requires new proc-macro crate infrastructure the workspace doesn't currently have; the trait-impl form delivers the same property without the infrastructure.
- Marker trait + `inventory` crate (link-time registration) — adds a new runtime dep; `syn` source-parse achieves the same discoverability at test time without the runtime cost.
- Defer to chunk plan — the marker form is the cross-chunk symbol every chunk introducing a pub enum attaches to; deferring leaves the chunk-plan author guessing what form downstream chunks should use, re-introducing the implementability gap the round-6 review surfaced.

## 2026-05-13 — `DerivedKind` is single source-of-truth; `is_derived()` delegates

**Decision:** Inside the `complete-regenerators` chunk, `StructuralModifier::is_derived()` in `compiler/src/ir/mod.rs` is rewritten to delegate to `DerivedKind`: `self.derived && DerivedKind::try_from(&self.modifier_type).is_ok()`. The existing 4-variant `matches!` literal in `is_derived()`'s body retires. `DerivedKind`'s variant set becomes the **single source-of-truth** for which `StructuralType` variants are derived; `is_derived()` becomes a delegated predicate. Adding a fifth derived `StructuralType` requires only one step — extend `DerivedKind` with a corresponding variant — which then forces the inner exhaustive-match arm in `regenerate_derived_kinds`'s inner function at compile time AND auto-flips `is_derived()`'s output for the new variant (because `DerivedKind::try_from` now succeeds for it). The outer dispatch arm continues to silently no-op on `Err` since the `kinds` argument is built upstream by `collect_stripped_kinds`, which filters by `is_derived()` — and `is_derived()` returns true only when `DerivedKind::try_from` succeeds, making `Err` at the outer arm structurally unreachable.

**Why:** Round 5 chose to introduce `DerivedKind` to escape an exhaustiveness-over-`StructuralType` defect. Round 6 found that the round-5 chosen design had a NEW defect on a different vector: the outer arm's silent-no-op-on-`Err` reproduced today's `_ => {}` deferred-sink behavior on the exact regression class the chunk claimed to close (a future contributor flipping a fifth `StructuralType` variant to derived in `is_derived()`'s `matches!` without extending `DerivedKind` would cause `TryFrom` to return `Err`, the outer arm to no-op, and the inner exhaustiveness check to never reach the new variant). Three resolution paths were considered. (A) Drop `DerivedKind` entirely; replace the inner match wildcard with `_ => unreachable!()` after the upstream filter. Reverses round-5's decision; smaller code footprint but retracts a structural commitment. (B) Bind the outer arm to panic on `Err`. Keeps `DerivedKind` but the enforcement is runtime, not compile-time. (C) Rewrite `is_derived()` to delegate to `DerivedKind::try_from`. Keeps `DerivedKind`, eliminates the parallel encoding (the set is encoded once in `DerivedKind`'s variant list; `is_derived()` becomes a derived predicate), AND provides compile-time enforcement of the regression class — adding a derived variant requires extending `DerivedKind`, which forces the inner-match update. Path C dominates: smaller diff than (A), stronger enforcement than (B), and the CLAUDE.md "no parallel representations" rule is honored (one encoding of "which `StructuralType` is derived", in `DerivedKind`'s variant list). The brief Goal 5 verifier ("derived-structural regenerators are complete and corpus-matched") is honored unchanged; the chunk's atomic-landing binding (2026-05-12 "Complete-regenerators chunk lands `PoolReplacement` regenerator and `generate_char_selection` body-shape correction atomically") is preserved because Path C is an internal mechanism amendment, not a chunk split.

**Rejected:**
- Path A (drop `DerivedKind`) — reverses round-5's structural commitment, retracts compile-time enforcement of the derived-allowed-set, and the inner-match's `_ => unreachable!()` arm gives only runtime enforcement (the regression mode is detectable only when the corpus produces the unreachable case, not at compile time of the new variant).
- Path B (panic on `Err` in outer arm) — keeps `DerivedKind` without making it serve its purpose; the regression mode is detectable at first test run (panic message), not at compile time when the contributor adds the unbacked derived variant.
- Path D (split the chunk into regenerator-bodies + derived-dispatch-exhaustiveness siblings) — violates the 2026-05-12 atomic-landing binding; both regenerator edits land in the same dispatch function (`regenerate_derived_kinds`) and share the same four-mod regenerator dogfood, so splitting doubles overhead without independent dogfood.

## 2026-05-12 — Chunk landing order: typed-NonSummon-payload → typed-summon-extractor → single-finding dedupe

**Decision:** The compiler-invariant-completions feature's chunks land in three ordered phases: (1) the typed-NonSummon-payload chunk retypes `ItempoolItem::NonSummon { content: String }` to `NonSummon(NonSummonEntry)` as its own atomic chunk; (2) the typed-summon-extractor chunk lands as a single atomic follow-up, bundling the real summon classifier, the `Finding.buckets` / `includes_boss` migration, and the `ReplicaItem` nested-egg schema widening per the brief's "in the same commit" prose; (3) the single-finding dedupe chunk lands after the typed `Finding` fields exist, so X003 and V020 dispatch on the typed payload rather than `Finding.message` substring scans. Other Goals (harvester-determinism, variant-evidence audit, complete-regenerators, vocabulary-cleanup, summon-name-rename) land in independent chunks whose DAG ordering against these three is open to the engineering plan.

**Why:** No parallel-representation state between landings (SPEC §3.7). The typed `NonSummonEntry` is in tree before any classifier produces typed entries, so the classifier can route non-matches to `NonSummonEntry::Unclassified` without inventing a parallel typed-vs-raw shape. The typed-summon-extractor chunk's three concerns land together because they are mechanically interlocked: the classifier produces `ReplicaItem` values whose schema is widened by the same chunk; the `Finding` typed-bucket migration arrives alongside the rules that produce findings against the classifier's output. Splitting the typed-summon-extractor chunk fragments the `Finding` migration away from its producer and forces the single-finding dedupe chunk to coordinate across two prior landings rather than one.

**Rejected:**
- Mega-chunk doing typed-NonSummon-payload + typed-summon-extractor + `Finding` migration + nested-egg schema all atomic — fails the ai-development "smallest useful slice" principle; one chunk doing 1000+ lines across three independently-shippable invariants is unreviewable.
- Splitting the typed-summon-extractor chunk into classifier / `Finding`-fields / nested-egg sibling chunks — the brief's typed-summon-extractor Goal commits to "in the same commit" for the schema widening; splitting fragments the `Finding` migration from its producer and creates a DAG edge from the typed-fields chunk to the single-finding dedupe chunk that doubles as a parallel-representation risk window.
- Landing the single-finding dedupe chunk before the typed-summon-extractor — V020 / X003 would dispatch on `Finding.message` substring scans until the typed fields land, leaving deferred-correctness state on `Finding`'s shape that the brief's "no deferred correctness" rule excludes.

## 2026-05-12 — `ReplicaItem` nested-egg schema is a recursive sum

**Decision:** The `ReplicaItem` schema widening to model nested enemy templates uses a recursive sum where the enemy slot carries an inner enemy via an optional boxed self-reference. The brief's typed-summon-extractor Goal property is strengthened in the same edit: "no nested-egg bytes silently lost AND every depth-N nesting in the source bytes is structurally encoded in the IR (flat sequences are excluded)."

**Why:** SPEC §3.6 "make invalid states unrepresentable" — the nesting is a containment relation, and encoding it as a recursive sum keeps the relation in the type at compile time. A flat `Vec<String>` admits reorderings of the sequence that change meaning (a parallel-representation hazard at the value level); a 1-level-capped optional-box (e.g. `enemy_template: String + nested_egg: Option<NestedEgg>` where `NestedEgg` is non-recursive) ships exactly the corpus-evidenced depth-2 shape per chunk-impl rule 3 but requires a new variant landing if a future deeper nested egg ever surfaces. The recursive sum's added flexibility carries no scope cost (one variant declaration, one `Box`) and preserves SPEC §3.6's compile-time encoding. The feature's typed-NonSummon-payload Goal already commits to a typed recursive sum (`NonSummonEntry` with `Box<NonSummonEntry>` payloads across its variants per the chunk plan), so the recursive shape is the established pattern this feature is landing — the nested-egg widening reuses it rather than introducing a new pattern.

**Rejected:**
- Flat `Vec<String>` of templates (positionally encoded depth) — admits reordering the sequence without changing the bytes; defeats the "structurally encode the nesting relation" principle and is a SPEC §3.7 parallel-representation hazard.
- 1-level-capped optional-box (non-recursive `NestedEgg` struct) — ships exactly the corpus-evidenced shape per chunk-impl rule 3, but a future depth-3 nested egg requires a new variant landing. The recursive shape's added flexibility carries no scope cost (one variant, one `Box`) and preserves SPEC §3.6's compile-time encoding without committing to unbounded depth at runtime.

## 2026-05-12 — Variant-evidence audit walks transitive closure of input-bytes-determined enums

**Decision:** The variant-evidence audit walks the transitive closure of input-bytes-determined enums reachable from `ModIR` via field traversal, not only top-level enum fields of `ModIR`'s direct children. Every new IR-reachable enum becomes audit-covered without per-enum opt-in. This binding supersedes the 2026-05-08 "Audit covers two shape classes" entry on the walk-depth question (that entry remains the source-of-truth for the two-class scope; this entry binds the walk depth across both classes).

**Why:** The brief's typed-NonSummon-payload Goal verifier asserts "audit extends automatically to walk `NonSummonEntry`'s variants as in-scope IR enum variants" — recursive transitive walk makes this property mechanically true: when `NonSummonEntry` lands carrying embedded `OuterWrap` / `CompositionComponent` / etc. enums (per the chunk plan), each becomes audit-covered for free without amending an opt-in list. Per-enum opt-in re-introduces the unevidenced-shape failure mode the audit exists to prevent — a contributor lands a new enum reachable from `ModIR` without an opt-in entry, and the audit silently misses unevidenced variants. The project's class-defined enforcement pattern is established by the 2026-05-08 "Variant-deletion bundle is class-defined" entry; this audit follows the same shape.

**Rejected:**
- Per-enum opt-in via a code-side enumeration list — fails on coverage growth; a new enum that lands without an opt-in entry is unaudited, defeating the audit's role as a brief-anchored invariant. Class-defined enforcement is the project's preferred pattern.
- Limit recursion depth to a fixed bound — implementation detail the audit picks at chunk-authoring time; the property bound here is "every reachable input-bytes-determined enum is in scope", not "every reachable enum within depth N".

## 2026-05-08 — Determinism audit requires harvester core invokable outside `cargo build`

**Decision:** Goal 3's verification mechanism, for any practical CI determinism check, requires the harvester core to be callable from a `compiler/tests/` integration test or a separate cargo binary target. Today the harvester functions are private to `compiler/build.rs` with no library import path, so test-time invocation requires extracting the pure core into a library module. The engineering plan owns the structural choice — factor the core into `compiler/src/harvester/` (or another module) with `build.rs` reduced to a thin shell, or another arrangement that delivers test-time invocability under the input-shape and SPEC §3.4 constraints above.

**Why:** Goal 3 commits to a verifiable property the codebase's current shape cannot deliver without restructuring access to the harvester core. The brief is committed to the property without naming the structural enabler; the practical-CI mechanisms the brief enumerates (mocked clock source, separate harvester-runner binary, in-process double-invocation) all require reaching the harvester logic from outside a `cargo build` invocation. Surfacing the enabler in the brief's Goal 3 prose would violate P-BRIEF-WHAT-NOT-HOW (architecture detail at the brief layer); placing it in `decisions.md` keeps the brief property-level and the implementation enabler engineering-plan-actionable.
